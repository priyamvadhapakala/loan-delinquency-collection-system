# REST API Documentation

## Local setup and response format

Start Flask from `backend` with `python run.py`. The base URL is
`http://127.0.0.1:5000`; endpoints use the `/api` prefix. Run the frontend at
`http://127.0.0.1:5500` to use the configured local browser CORS policy.

Successful responses use a JSON `data` property. Collection reads return an
array in `data`; resource reads return an object. Errors use:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "A human-readable explanation."
  }
}
```

Amounts are integers in minor currency units (100 INR paise = INR 1). Dates use
`YYYY-MM-DD`; event timestamps use UTC `YYYY-MM-DDTHH:MM:SSZ`. Identifiers are
generated by services.

## Endpoints

### Health and portfolio calculations

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Check Flask and SQLite connectivity |
| GET | `/api/delinquency?as_of=YYYY-MM-DD` | Calculate schedule-based balance and delinquency for all loans |
| GET | `/api/loans/{loan_id}/balance?as_of=YYYY-MM-DD` | Calculate one loan's live balance and overdue installments |
| GET | `/api/reports/delinquency?as_of=YYYY-MM-DD` | Return server-calculated overdue totals and delinquency categories |

`as_of` is optional and defaults to the server's current date. A balance
includes `outstanding_principal_minor`, `outstanding_interest_minor`,
`outstanding_balance_minor`, `arrears_amount_minor`, `days_past_due`,
`delinquency_bucket`, and remaining overdue installments. An installment is
overdue when its date is strictly before `as_of` and it has an unpaid
principal or interest amount. DPD is measured from the oldest unpaid overdue
installment. Buckets are `current`, `1-30`, `31-60`, `61-90`, and `91+`.

### Customers

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/customers` | List customers |
| GET | `/api/customers/{customer_id}` | Get one customer |
| POST | `/api/customers` | Create a customer |
| PATCH | `/api/customers/{customer_id}` | Update one or more customer fields |
| GET | `/api/customers/{customer_id}/loans` | List the customer's loans |

Create requires `first_name`, `last_name`, and `email`. Editable fields are
`first_name`, `last_name`, `email`, `phone`, and `customer_status`. Customer
creation and updates are audited without copying customer contact values into
audit details.

### Loans and installments

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/loans` | List loans; optional `customer_id` filter |
| GET | `/api/loans/{loan_id}` | Get one loan |
| GET | `/api/installments` | List installment schedules and allocation totals |
| GET | `/api/installments/{installment_id}` | Get one installment |
| GET | `/api/loans/{loan_id}/installments` | List a loan's installment schedule |

### Payments

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/payments` | List payment history; optional `loan_id` filter |
| POST | `/api/payments` | Record a payment and server-calculated allocations |

POST requires `loan_id`, positive integer `amount_minor`, `payment_method`,
and `external_reference`. Optional fields are `currency_code` and UTC
`received_at`. Accepted methods are `bank_transfer`, `debit_card`, `cash`,
`mobile_wallet`, `direct_debit`, and `other`. The currency must match the loan.
The service allocates against due installments by due date, applying interest
before principal. It reports allocated and unallocated amounts. Payment and
allocation updates are transactional and audited.

### Collection cases

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/collection-cases` | List cases with calculated balance, account status, contacts, and promises |
| GET | `/api/collection-cases/{case_id}` | Get one case with related records |
| POST | `/api/collection-cases` | Create or return the active case for an overdue loan |
| PATCH | `/api/collection-cases/{case_id}` | Update case lifecycle status |

Case creation requires `loan_id`; optional `case_source` is `system`, `manual`,
or `import`. A case requires positive arrears. Priority is low below 31 DPD,
medium at 31–60 DPD, and high at 61+ DPD. At most one active case per loan is
allowed. Status values are `open`, `in_progress`, `resolved`, and `closed`;
transitions are validated and audited.

### Contact preferences and contact attempts

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/customers/{customer_id}/contact-preference` | Read current settings; `data` may be `null` |
| PUT | `/api/customers/{customer_id}/contact-preference` | Save current contact settings |
| POST | `/api/collection-cases/{case_id}/contact-attempts` | Validate and record a contact attempt |
| POST | `/api/contact-holidays/{holiday_date}` | Explicitly register a test-policy holiday with JSON `label` |
| GET | `/api/audit-events` | Read audit history; optional `entity_type` and `entity_id` filters |

Preference fields include `preferred_channel` (`phone`, `email`, `sms`,
`letter`, or `none`), `consent_status` (`granted`, `not_required`, or
`withdrawn`), optional `contact_window`, `timezone`, `allowed_contact_start`,
`allowed_contact_end`, `weekend_contact_allowed`, `holiday_contact_allowed`,
and nullable `allowed_channels` array. The UI configures timezone and hours
before attempting contact. The service denies attempts when timezone or hours
are absent, applies channel restrictions only when explicitly configured, and
defaults weekend/holiday permissions to false. Only explicitly configured
holiday dates are checked. Denied attempts are recorded in the audit history
and return HTTP 403; permitted attempts create a `ContactAttempt` and audit
event.

This neutral policy is **test-only and is not legal compliance certification**.
It does not assume jurisdiction-specific contact hours or infer holidays.

Attempt JSON fields:

```json
{
  "attempted_at": "2026-11-11T10:00:00Z",
  "channel": "email",
  "outcome": "message_sent",
  "notes": "Synthetic test record."
}
```

### Account dispute and hardship status

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/loans/{loan_id}/account-status` | Read dispute, hardship, and debt status |
| PUT | `/api/loans/{loan_id}/account-status` | Update one or more of those statuses |

Allowed `dispute_status`: `clear`, `disputed`, `resolved`; `hardship_status`:
`none`, `active`, `resolved`; `debt_status`: `unverified`, `confirmed`.
A debt cannot be saved as both disputed and confirmed. Updates are audited.

### Promise-to-Pay

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/promises` | List promises with related case, loan, and customer IDs |
| POST | `/api/collection-cases/{case_id}/promises` | Create a promise against current arrears |
| PATCH | `/api/promises/{promise_id}` | Mark a pending promise kept, broken, or cancelled |
| POST | `/api/promises/evaluate` | Evaluate overdue pending promises; optional JSON `as_of` |

Create requires UTC `promised_at`, `due_date`, and positive integer
`amount_minor`. The case must be active, the account must not be disputed,
arrears must be positive, and the promise amount cannot exceed arrears.

Promise evaluation uses posted payments received after the promise timestamp
and on/before its due date. A payment can satisfy at most one eligible promise;
when windows overlap, evidence is allocated by earliest due date, then promise
time and ID. `kept` status requires sufficient evidence; `broken` status
requires the due date to have passed and insufficient payment evidence.
Evaluation and status changes are audited.

### Anomalies and report

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/anomalies/detect` | Run repeat-safe detection; optional JSON `as_of` |
| GET | `/api/anomalies?status=active` | List anomaly records; optional `status=active` or `resolved` |
| GET | `/api/reports/anomalies?as_of=YYYY-MM-DD` | Run detection and return report counts and findings |

The five categories are `paid_account_in_collection`,
`contact_outside_allowed_window`, `payment_wrong_installment`,
`promise_exceeds_arrears`, and `disputed_debt_confirmed`. Detection is based on
business and compliance records. It does not read `AnomalyGroundTruth`;
ground-truth labels are separate synthetic evaluation data. A unique
type/reference pair prevents duplicate records on repeated runs. Existing
findings become resolved when the condition is absent in a later run.

## CORS and local development

Only the exact origin `http://127.0.0.1:5500` receives CORS headers. Wildcard
origins are not used; `localhost:5500` is a different origin and is not
permitted. Keep the Flask server bound to `127.0.0.1` during development.

## Common error responses

| HTTP status | Meaning |
|---|---|
| 400 | Invalid or incomplete input |
| 403 | Contact attempt denied by configured test policy |
| 404 | Resource not found |
| 409 | Duplicate or invalid lifecycle/state transition |
| 415 | Request body is not JSON where JSON is required |
| 503 | SQLite operation failed |
| 500 | Unexpected internal error; details are logged, not returned |

All errors use the JSON `error.code` and `error.message` shape.
